# Remotica frontend

Vite + React 19 (JavaScript, not TypeScript) + Tailwind CSS v4 + shadcn/ui (Nova/radix-nova preset, Lucide icons) + react-router-dom v7.

## Commands

- `npm run dev` — dev server (needs Node on PATH; installed via nvm on this machine)
- `npm run build` — production build
- `npm run lint` — oxlint
- `npm run format` / `npm run format:check` — Prettier (`.prettierrc.json`; defaults mostly match, double quotes + semicolons + es5 trailing commas)
- Adding shadcn components: `npx shadcn@latest add <name>` (run from `frontend/`, config is `components.json`)

## Design tokens

All in `src/index.css`, custom dark-only theme (no light mode) mapped into a Tailwind v4 `@theme inline` block. Key values:

- `--background: #1b1c1a`, `--foreground: #e7e7e2`, `--card: #242524`
- `--primary: #6b8f63` (sage green), `--primary-foreground: #10130f`
- `--muted-foreground: #9aa896`, `--border: #33352f`
- `--brand-from: #b2c9ad` / `--brand-to: #4b5945` — gradient used for the "REMOTICA" wordmark
- `--radius: 0.65rem`
- Font: "Kumbh Sans" (loaded via `<link>` in `index.html`, not self-hosted)
- Temperature colors live separately in `src/lib/temp-colors.js` — hotend `#d95926` (orange), bed `#3987e5` (blue), validated as a categorical pair via the `dataviz` skill. Shared between `TempDial` and `TemperatureGraph` so they can't drift apart — always import from there, never hardcode.
- Motion tokens live in `src/styles/motion.css` (imported from `index.css`) — see "Motion" below.

## Motion

Everything animated is driven from `src/styles/motion.css`. It registers easing (`ease-soft`, `ease-spring`, `ease-smooth`) and animation (`animate-rise`, `animate-fade`, `animate-pop`, `animate-sheen`, `animate-halo`) utilities through a Tailwind v4 `@theme` block, so they're used as ordinary classes rather than hand-written CSS at each call site.

- **Kill switch**: adding `data-motion="off"` to `<html>` in `index.html` disables every transition and animation app-wide — including the inline Tailwind `transition-*` utilities scattered through components, since the rule is a `*` selector with `!important`. That's the intended way to evaluate or drop the whole look without unpicking it component by component. `prefers-reduced-motion: reduce` applies the same rules automatically.
- The disable rules set `animation-duration: 0.01ms`, **not** `animation: none`. Entrance animations start from `opacity: 0`, so cancelling them outright would leave content invisible; running them instantly is what guarantees the page still ends up on screen.
- Entrance animations use `animation-fill-mode: backwards`, not `both`, deliberately: `both` would leave a `transform` on the element forever after, which creates a containing block for any `position: fixed` descendant.
- `.motion-stagger` on a container cascades its direct children in — the container carries both the animation and the per-child delay, so a list built from `.map()` needs no index plumbing. Applied to the two dashboard columns, the About page's card grids, and the on-device file list.
- Route changes animate via a wrapper in `App.jsx` keyed on `location.pathname` — the key is what forces a remount, which is what replays the animation. Enter-only; there is no exit animation, because holding the old page on screen after a click makes navigation feel slower even though it looks busier.
- House style, from the file's own header: nothing loops except indicators reporting something genuinely live (the connection halo, the camera "Live" dot, the print progress sheen), and **nothing animates on a value the printer reports** — a temperature that slides on every update is harder to read, not easier. `TempDial`'s heating glow is static for that reason.
- Several components carry a React `key` purely to make a state change animate rather than mutate in place — `ConnectionStatus` (on `connected`), `CameraView`'s live badge (on `liveStatus`), `Settings`' suggestion panel (on `suggestionView`) and spec list (on `selectedId`). Removing those keys is silently a behaviour change, not a cleanup.

## Structure

- `src/pages/` — route-level components; all four routes are real now (`Dashboard.jsx`, `Settings.jsx`, `About.jsx`, `System.jsx`). `System.jsx` (2026-08-08) reports host-level status from `GET /api/system` — version, uptime, serial port, data directory, free space — and carries the start-on-boot switch. It re-fetches every 5s so uptime advances (deliberately far slower than the printer's 300ms tick; nothing here moves fast and the endpoint shells out to `systemctl`). **The switch is disabled whenever `managed` is false**, which is the normal state in a dev checkout: there's no systemd unit to change, so it shows an explanation rather than a control that silently fails — and the backend 409s that case too, so the UI and the API agree rather than the UI merely hiding a failure. The toggle updates optimistically and reverts on error, because a `systemctl` round trip is long enough that an un-moved switch reads as broken. `Placeholder.jsx` is gone — it had no remaining users once System became real. `About.jsx` (2026-08-04) is a static marketing/status page — what Remotica is, the three things that define it, an explicit "working vs. not verified yet" split, the stack, and the licence disclaimer. It has no state and calls no API. Its two honesty-critical bits are the safety alert at the top and the "not verified yet" column: **both are claims about real hardware and go stale**, so they need updating alongside `ROADMAP.md` and the root `README.md` rather than being left to drift. `Settings.jsx` is where the printer gets identified, rebuilt (2026-08-03) around two panels because the previous single-form version read as one undifferentiated pile of numbers:
  - **"Suggested printer"** — connection badge, then what `GET /api/printer-suggestion` reports the attached printer is, with the raw `M115` reply shown underneath as the _evidence_ for that guess (labelled "What the printer reported"). Showing the evidence is the point: the closing note tells the user Remotica only inferred this from a model name and they should confirm it themselves, which they can't do if the basis is hidden. Purely informational — this panel never applies anything.
  - **"Choose your printer"** — one `Select` holding the suggestion (in its own "Suggested" group, and filtered out of the main list so it isn't listed twice), then the rest of `GET /api/printer-database`, then "Enter specs by hand" (`MANUAL_ID`). **Progressive disclosure**: the six spec fields don't render at all until something is selected — read-only for a preset, editable inputs plus a free-text name for manual. Nothing is applied until "Use this printer" is pressed, so a suggestion being pre-selected is only a proposal.
  - Initial selection is chosen once by an effect and then frozen behind `userPickedRef` so a suggestion arriving late (printer connects while the page is open) can't silently overwrite a choice already made: unconfigured profile → the suggestion; already-configured → whichever database entry matches the saved `printerName`, else manual with the saved numbers prefilled.
  - The profile's `printerName` (renamed from `detectedName` on 2026-08-03, since it now also carries preset and hand-typed names) is what "In use right now" shows and what `POST /api/profile` persists.
- `src/components/control/` — the printer control panel ("printer blueprint" design: top-down bed schematic for XY jog, vertical drag-rails for Z/E, temp dials, live temperature graph). XY/Z/E jog is fixed at 1mm — no step-size selector, that was deliberately removed. While a print is active (printing/paused), the whole panel dims with a lock overlay — see `ControlPanel.jsx`. Same treatment (2026-08-01) while the printer profile itself isn't configured yet (`profile.source === "default"`), except that overlay is interactive — a "Choose printer" button linking to `/settings` — since there's a real next step, unlike mid-print where none exists.
- `src/components/dashboard/` — left-panel dashboard pieces: connection status badge (shows a best-effort printer name too, via `parsePrinterName()` on the backend's firmware hint), gcode dropzone/upload, `OnDeviceFiles.jsx` (collapsible browser for gcode files already stored on the backend, with thumbnail/print-time preview, select-to-print, and delete), and `CameraView.jsx` (right column, live webcam preview — `GET /api/camera` is checked once on mount; if available, renders `<img src="/api/camera/stream">` directly, since browsers display MJPEG multipart streams natively with no client-side video code needed. **Hot-plug (2026-08-08):** `GET /api/camera` is polled continuously for the component's whole life, not checked once on mount — each poll makes the backend re-check the `/dev/video*` node list, so plugging a camera in shows it with no page refresh. `streamBroken` is deliberately **not** a one-way latch (it used to be, which is why a replugged camera never came back): it clears whenever the backend reports no camera, and a reconnect effect rebuilds the stream after `RECONNECT_DELAY_MS` when a camera is available again. Reconnecting works by bumping `streamKey`, which both remounts the `<img>` and cache-busts its URL — React would otherwise reuse the element and the browser would reuse the dead response. Two triggers: the `<img>`'s `onError` (the usual one — the backend ends the response when its capture thread dies), or frames stalling while the backend reports `streaming: false`. Falls back to a "no camera detected" placeholder when the backend reports none, and a distinct "reconnecting" state when a camera exists but the stream doesn't. Fullscreen button toggles the whole camera card via the native Fullscreen API. While streaming, polls `GET /api/camera`'s `frameSeq` counter every 1.5s and shows a "Live"/"No new frames" badge depending on whether it's advanced within the last 4s — an `<img>` showing an MJPEG multipart stream gives no reliable per-frame browser event to hook into, so this instead piggybacks on the frame-sequence counter the backend's capture thread already tracks internally).
- `src/hooks/` — `use-printer-state.js` (live printer state: initial `GET /api/state` fetch + `/api/ws` WebSocket subscription, with auto-reconnect if the connection drops. The `jog`/`home`/`setHotendTarget`/`setBedTarget` it returns all go through `requireConnected()` first, which shows a toast and skips the API call entirely if `state.connected` is false, instead of letting it hit the backend and come back as a 502), `use-gcode-file.js` (picks + uploads a local gcode file, parsing its thumbnail/print-time client-side for instant feedback), `use-file-preview.js` (fetches + caches thumbnail/print-time for any filename already on the backend, used by the "on device" browser).
- `src/lib/` — `api.js` (thin fetch wrapper around every backend REST route), `gcode-thumbnail.js` + `gcode-print-time.js` (parse slicer-embedded metadata straight out of gcode file text — used both for a freshly-picked local file and for previewing files already on the backend), `temp-colors.js`, `utils.js` (`cn()` helper). The printer profile (bed size, max Z, etc.) is no longer hardcoded here — it's fetched from `GET /api/profile`.

## Conventions

- No new features/pages/content without asking first — this has been explicit from the user throughout. Visual/tooling improvements to existing content are fine to proceed on directly.
- No code comments unless the _why_ is genuinely non-obvious (a workaround, a hidden constraint) — not what the code does.
- All printer/job state comes from the real backend now (`usePrinterState`) — see root `CLAUDE.md` for what the backend still doesn't do for real (actual print streaming, serial hardware verification).
- Anything that changes the printer physically (jog, home, temp, print start/pause/stop) sends exactly one API call per discrete user action — never on every intermediate pointer-move of a drag. `BedSchematic`'s drag-to-jog previews locally and commits a single delta on release, same pattern `AxisRail` already used.
- Global toasts (shadcn's `sonner` — `src/components/ui/sonner.jsx`, mounted once in `App.jsx`) are the pattern for "you tried to do something physical but it can't happen right now" feedback — e.g. `use-printer-state.js`'s `requireConnected()` and `Dashboard.jsx`'s print-start button both toast "Printer is disconnected" rather than letting the action silently no-op. `theme` is hardcoded to `"dark"` on the `Toaster`, not read from `next-themes` — this app has no light mode to switch between (see "Design tokens" above), so that dependency was deliberately left out of `package.json` even though `npx shadcn add sonner` normally pulls it in.
