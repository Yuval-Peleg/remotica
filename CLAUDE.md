# Remotica

An from-scratch, OctoPrint-inspired remote control dashboard for 3D printers. Dark/sage-green theme throughout. Not ready for real printer use yet — see README.md.

## Repo layout

- `frontend/` — the active app. See `frontend/CLAUDE.md` for details.
- `ROADMAP.md` — known gaps and planned work, roughly ordered by what matters most before real unattended printer use.
- `backend/` — C, using civetweb (embedded HTTP + WebSocket server) and cJSON, both vendored under `backend/third_party/`. See "Backend" below.
- `run.sh` — one-command launcher for a test session: builds the backend if needed; for real-hardware runs, offers a one-time `sudo`-gated install of `udev/99-remotica-serial.rules` (grants USB-serial access without needing `dialout` group membership or a logout/login — skipped for `--sim`, skipped if already installed and up to date, skipped if stdin isn't a terminal so it never hangs waiting for input nobody can give); starts the backend (`--serial auto` by default — real printer, auto-detected; `./run.sh --sim` for the simulator instead), starts the frontend dev server bound to all interfaces (`vite --host`, not just `localhost`) so other devices on the LAN can reach it too, waits for both to actually be reachable, prints the printer connection status plus the LAN URL (`http://<this machine's IP>:5173`, via `hostname -I`), and opens the dashboard in a browser on this machine. Ctrl+C stops both processes together (cleanly — killing background PIDs from a script needs care: `npm run dev` forks a real `vite` child rather than exec'ing into it, so the launcher execs straight into `node_modules/.bin/vite` instead, otherwise the actual process would survive as an orphan after `npm` was killed). This is still two separate processes under the hood (see "Deployment model" below) — it's a dev-mode convenience wrapper, not the eventual single-process production model.
- `udev/99-remotica-serial.rules` — the udev rule `run.sh` installs (with permission) so USB-serial printer access doesn't require `dialout` group membership. See the file's own header comment for the full reasoning (why `MODE="0666"` over the more targeted `uaccess` tag) and manual-install instructions if you'd rather not use `run.sh`'s prompt.
- `legacy-static/`, `images/` — old hand-built mockup, kept on disk for reference only. Gitignored on purpose — do not re-add to git without asking.

## Deployment model

Frontend and backend run as a **single process** on the same PC that's physically wired to the printer (same model OctoPrint uses). The backend serves the already-built frontend directly — no separate hosting, no CORS setup. Other devices reach it over LAN by browsing to that PC's IP. No accounts, no cloud relay, no port-forwarding. **Not built yet** — right now `run.sh` (or manually running each half) starts frontend and backend as two separate processes, backend serving the API and the Vite dev server serving the frontend with a proxy in between. See "Not done yet" below.

## Backend

- **Language:** C — deliberate choice, not a placeholder.
- **HTTP + WebSocket:** [civetweb](https://github.com/civetweb/civetweb) (MIT), one embeddable library for both. **Not Mongoose** — Mongoose looked like the obvious pick early on, but it's dual-licensed GPLv2/commercial with no permissive option, which would force this MIT-licensed repo to either go GPL or pay for a commercial license. civetweb is a permissively-licensed sibling (same original codebase lineage) with the same HTTP+WebSocket feature set, so it was swapped in instead. If any other C dependency gets added later, check its license before vendoring it — same issue could recur.
- **JSON:** [cJSON](https://github.com/DaveGamble/cJSON) (MIT).
- Both vendored as source under `backend/third_party/` (civetweb 1.16, cJSON 1.7.19) — no package manager, just `.c`/`.h` files compiled straight into the binary. Their upstream LICENSE files are kept alongside them.
- **Build:** `cd backend && make` → `backend/build/remotica-backend`. Run it from `backend/` (it uses relative paths for `data/profile.json` and `data/uploads/`, both gitignored — runtime-generated). Built with `NO_SSL` (no HTTPS needed on LAN) and `USE_WEBSOCKET` defined. Needs a C toolchain — install via `sudo apt-get install build-essential clang-format cppcheck`.
- **Target OS:** Linux first, headless-compatible (Ubuntu Server, no GUI needed). A Windows fork is planned for later; only the serial layer (POSIX `termios` → Win32 serial API) should need to change, since civetweb/cJSON are already cross-platform.

### Source layout (`backend/src/`)

- `main.c` — wires everything together: parses `--port <n>` (optional, defaults to 8080 — exists so `backend/tools/fake_marlin_test.py` can run a second backend against a pty without having to stop a real one already serving the dashboard) and `--serial <device>` (optional — omit it to use the simulator, which is the default; `--serial auto` scans for the device itself instead of needing an exact path, see `transport_serial_discover()`), starts civetweb, registers routes, runs a background thread that ticks the driver and broadcasts state roughly every 300ms. On shutdown, calls `job_manager_shutdown()` (stops/joins any in-progress print streaming thread) before disconnecting the driver, so the driver's connection can't be torn down while that thread is still using it. **Starting up without a printer connected is not an error** (it used to be — `--serial auto` finding nothing, or an explicit `--serial <device>` failing to open, used to make the whole backend exit): the backend now always starts regardless, and a background reconnect thread (`reconnect_thread_main`) retries `driver->connect()` every `RECONNECT_RETRY_INTERVAL_SECONDS` (5s) for as long as `state->connected` is false. Started/joined alongside the tick thread; only spawned for the real serial driver, since the simulator's `connect()` always succeeds immediately. See `transport_serial_create_auto()` below for the `--serial auto`-with-nothing-found-yet case specifically. This does not (yet) detect a printer going away mid-session (e.g. a live USB unplug) — see `ROADMAP.md`.
- `printer_state.h/.c` — `PrinterState`: the single shared, mutex-protected struct holding "what's true about the printer right now" (temps, position, connection, job status/progress — status is idle/ready/printing/paused). Everything else reads/writes through this.
- `printer_profile.h/.c` — bed size / max Z / min extrude temp, persisted to `data/profile.json`. The frontend fetches this from `GET /api/profile` on mount instead of hardcoding it.
- `transport.h` — `PrinterDriver`: the function-pointer interface (connect/disconnect/jog/home/set_target_temp/tick/send_gcode_line) that decouples the REST API and job manager from *how* commands actually reach the printer.
- `transport_sim.h/.c` — the default driver. No real hardware; fakes temperature drift and instant moves. Its `send_gcode_line` does just enough gcode parsing (G0/G1 moves incl. G90/G91/M82/M83 modal state, G28 home, M104/M140/M109/M190 target temps) to make a simulated print visibly drive the position/temperature UI, not just log lines.
- `transport_serial.h/.c` — the real driver, talks POSIX `termios` + G-code to an actual printer over USB. **Written carefully but only lightly tested against real hardware** — see the warning at the top of `transport_serial.h` before using `--serial` with a real printer. An Opus review (2026-07-31) found and fixed several serious concurrency/protocol bugs in this file (no lock serializing the three threads that touch the serial port, timeouts that could hang forever, stale-"ok" desync risk) — see git history around that date for the review and fix commits if you need the details. Print-streamed gcode lines are sent with a RepRap-standard line number + checksum (`gcode_checksum`/`send_checksummed_line`), negotiated at connect time via `M110 N0` with a clean fallback to plain lines for firmware that doesn't support it — catches bit corruption in transit (retried via the printer's `Resend:` reply) instead of silently executing a corrupted command. Verified against a real Linux pty pair standing in for hardware (`backend/tools/fake_marlin_test.py`), since real hardware wasn't available while writing it. `transport_serial_discover()` scans `/dev/ttyACM*`/`/dev/ttyUSB*` and probes each at the baud rates in `BAUD_RATE_OPTIONS` (currently just 115200 — 250000, used by some 32-bit boards, would need Linux's termios2/BOTHER ioctl mechanism for arbitrary baud rates, not implemented) for `--serial auto`. Its `send_gcode_line` doesn't track position from the gcode file it streams (no reliable firmware-agnostic way to query it back) — position readouts are known to lag reality during a real print.
  - **Reconnect without a device path** (2026-08-01): `transport_serial_create_auto()` builds a driver with no fixed `device_path` at all, for `--serial auto` when the startup scan finds nothing. Its `serial_connect()` re-scans via `transport_serial_discover()` on every call where the fd is still unset — both the first (failing) attempt and every later retry from `main.c`'s reconnect thread — so it's not tied to whatever `/dev/ttyACM*`/`ttyUSB*` path the printer happens to enumerate as. `transport_serial_create_from_discovery()` (the already-found-at-startup path) sets the same `auto_discover` flag, so if that connection is ever lost, reconnecting also re-scans rather than assuming the printer comes back on the same path. An explicit `--serial <device>` never re-scans — it only ever retries that exact path.
  - **First real-hardware verification (2026-08-01)**, against a real Ender 3 (stock Marlin 2.1.2.4): connect, `--serial auto` discovery, and live temperature polling all confirmed working end to end. Found and fixed two real bugs in the process, neither catchable by the pty test (which has no real UART timing) — both in `transport_serial.c`: (1) `TIMEOUT_MS_FIRMWARE_INFO` — M115's reply on Marlin 2.x includes an extended `Cap:` capability report (~40 lines) that measured ~7.6s end-to-end on this board, well past the previous 5s timeout, which made a real, correctly-responding printer look like "no printer found"; (2) `query_firmware_info()` was capturing the FIRST non-"ok" reply line as the firmware hint, but this board sends an unrelated `echo:SD card ok` line before the real `FIRMWARE_NAME:...` line — fixed to specifically look for a line containing `FIRMWARE_NAME:`, falling back to the first line only if none is found. **Not yet verified against real hardware** *(at the time of that session)*: jog, home, temperature-set commands, and actual print streaming (the checksum/resend path) — only connect/discovery/temperature-polling had been confirmed against a real printer at that point. A real print was attempted later the same day and immediately hit the two bugs in the next sub-bullets; the fixes for those are verified against the pty harness only and have **not** been re-run against the physical printer yet.
  - **Discovery/connect speed**: `--serial auto` used to pay for the DTR-triggered reset + boot-wait + M115 exchange TWICE — once to probe a candidate in `transport_serial_discover()`, then again from scratch for the real connection — since every open() of the port resets the board. `transport_serial_create_from_discovery()` now reuses the exact already-open, already-booted, already-queried connection discovery already established (`probe_device()` leaves the fd open and hands back the firmware info it already captured instead of closing everything and starting over), so there's only one reset/boot/M115 cycle total. Measured on the real Ender 3: ~25-30s down to ~12s end to end.
  - **First real-print attempt against real hardware (2026-08-01)**, same Ender 3: two more bugs, both found live and neither caught by the pty test as it stood (both are now covered by it — see `backend/tools/fake_marlin_test.py` scenarios C and D). (1) **False abort on a slow-but-legitimate move**: `command_timeout_ms()` gives an ordinary G0/G1 only `TIMEOUT_MS_NORMAL` (5s), and a travel move right after G28 measured just over that. Marlin was emitting `echo:busy: processing` keepalives the whole time (its standard host-keepalive protocol — an explicit "still working, don't give up on me"), but the wait loops skipped them as noise without extending the deadline, so a healthy printer was declared a driver failure and the whole print aborted after essentially one move. Fixed with `is_busy_line()` + `deadline_extend()`: a busy-keepalive now restarts the command's allowance in both `send_and_wait_for_ok()` and `send_checksummed_line()`. This is deliberately NOT a contradiction of the "the budget is shared, it is NOT restarted per line" comment on deadlines — that reasoning is about M115's bounded capability dump, whereas a keepalive carries real information (progress is being made), and resetting on it is what OctoPrint/Printrun do too. Bounded by `TIMEOUT_MS_BUSY_CAP` (30 min) so the wait still terminates, and deliberately scoped to `busy: processing` only — Marlin's `paused for user`/`paused for input` states repeat for as long as a *human* takes to respond, and extending on those could block the streamer thread (and with it `job_manager_shutdown()`, and with that Ctrl+C) indefinitely. (2) **The abort-safety sequence could silently no-op — the serious one, see the `job_manager.c` bullet below.**
  - **Stale line numbers after a failed line (2026-08-01, safety-relevant)**: `send_checksummed_line()` only advances `impl->next_line_number` on a confirmed "ok" — correct for a resend (the firmware wants the same N again), but it meant a line that failed outright left N pointing at a number already put on the wire. Marlin treats a repeated line number as a retransmission and re-acks it *without re-parsing the body*, so the next command — different text, stale N — got a cheerful "ok" and was thrown away. The command that lands in that slot is not arbitrary: a failed line is exactly what makes `job_manager.c` abort the print and immediately send `M104 S0`/`M140 S0`/`M107`. Observed live: hotend and bed sat at full print temperature for 20+ minutes after an "aborted" print while the backend reported the shutdown as successful (mitigated at the time by `POST /api/temp`, which goes through the non-checksummed path and was unaffected). Fixed with `resync_line_numbers()`: any checksummed line that fails without a confirmed "ok" sets `needs_line_number_resync`, and the next checksummed send re-runs the `M110 N0` negotiation (unnumbered, so it can't itself be swallowed as a duplicate) before sending anything. Deliberately *not* "just increment N on failure too" — the failed line was never confirmed received, so jumping past its number risks the opposite desync, with the firmware demanding a resend of a number this driver has already moved beyond. Also deliberately lazy/inside the transport layer rather than pushed from `job_manager.c`: the stale number is this driver's own protocol state, so repairing it here protects every later checksummed line — not just the abort-safety sequence but also the first line of the next print started on the same connection, which would otherwise have been silently dropped the same way — and it keeps `PrinterDriver`'s interface unchanged, so `transport_sim.c` needs no matching concept it has no use for.
- `job_manager.h/.c` — gcode upload (to `data/uploads/`, with filename validation against path traversal), the print job state machine (idle → ready → printing ⇄ paused → ready), and "on device" file management (list/select/delete previously-uploaded files — files are kept on disk until explicitly deleted, so they can be reprinted without re-uploading). **Real print streaming**: `job_manager_start_print()` launches a dedicated background thread (`streamer_thread_main`) that reads the queued gcode file line by line (stripping blank/comment lines), sends each real line to the driver via `send_gcode_line()`, and tracks progress as lines-sent/total-lines — pause/resume/cancel are all handled by the thread polling `state->job.status` and a small cancel flag between lines. Runs on its own thread (not the shared tick loop) specifically so a multi-hour print doesn't block temperature polling or WebSocket broadcasts. Uploading, selecting, jogging, or homing while a print is running/paused is refused with 409 (see `api_handlers.c`) — those used to be able to silently kill or corrupt an in-progress print. Cancelling or losing the printer mid-print now runs a safety sequence (`send_abort_safety_sequence`: heaters off, fan off, small Z lift, steppers disabled) before the job settles into its final status. **That sequence used to be able to silently no-op** on the driver-failure path (2026-08-01, found live): it sends through the same `send_gcode_line()` as print lines, and the line number the just-failed line left behind made Marlin re-ack `M104 S0` without executing it — heaters stayed on while the backend reported success. Fixed in `transport_serial.c` (see the "Stale line numbers after a failed line" sub-bullet above); nothing in this file changed, but it's worth knowing that this sequence's effectiveness depends on the transport layer resynchronising its line numbering after a failure, and that `backend/tools/fake_marlin_test.py` scenario D is what now guards it.
- `api_handlers.h/.c` — every REST route: `GET /api/state`, `POST /api/jog`, `POST /api/home`, `POST /api/temp`, `GET`+`POST /api/profile`, `POST /api/upload?filename=...`, `POST /api/print/start`, `POST /api/print/pause`, `POST /api/print/resume`, `POST /api/print/cancel`, `GET /api/files`, `GET /api/files/content?filename=...`, `POST /api/files/select?filename=...`, `POST /api/files/delete?filename=...`. Also where jog/temp inputs get clamped to the profile's physical limits and the cold-extrusion safety check lives (mirrors the frontend's `canExtrude` check, enforced server-side too since a backend shouldn't trust a frontend-only safety check for something with a physical consequence).
- `ws_broadcaster.h/.c` — tracks connected WebSocket clients at `/api/ws` and pushes a state snapshot (same shape as `GET /api/state`) to all of them every tick.
- `camera.h/.c` — optional webcam support, entirely independent of the printer driver. `camera_init()` scans `/dev/video*` for a V4L2 device that supports MJPEG capture (the large majority of real USB webcams) and remembers it — a passive metadata query only, verified against a real laptop webcam (2026-08-01). **Capture is deliberately lazy**: opening/activating the camera and starting the background capture thread only happens the first time a client requests `GET /api/camera/stream` (`ensure_capture_started()`), not just because the backend is running — a webcam has real privacy implications a 3D printer's serial port doesn't, so it shouldn't turn on unattended. `GET /api/camera` reports `{available, name, frameSeq}` without ever activating anything — `frameSeq` is `0` until capture actually starts, then advances by one per captured frame (whatever `capture_thread_main` has most recently written to `g_camera.latest_frame_seq`); the frontend polls it while a stream is open to tell "camera is live" apart from "picture looks frozen" (see `CameraView.jsx` in `frontend/CLAUDE.md`), since an `<img>` showing an MJPEG stream gives no reliable per-frame browser event on its own. The actual mmap-based V4L2 capture loop and MJPEG multipart streaming (`camera_stream_handler`) are **written carefully but NOT verified against real frame capture** — same "untested against real hardware" posture as `transport_serial.c` — test cautiously before relying on it. `main.c` raises civetweb's `num_threads` (4→8) since each open camera-stream viewer ties up a worker thread for as long as the tab stays open, and calls `camera_shutdown()` before `mg_stop()` specifically so an open browser tab can't make shutdown hang.

The original `POST /api/command` smoke-test route and its frontend dev panel (`BackendConnectionTest.jsx`) have been removed now that the frontend talks to the real endpoints above.

### Not done yet

- **The serial driver is unverified against real hardware** (see above) — this matters more now that a real print would actually stream real gcode to it line by line, not just jog/home/temp commands.
- **The backend doesn't serve the built frontend yet** — right now they're two separate processes talking over the Vite dev proxy (`frontend/vite.config.js`, `ws: true` for `/api/ws` too). The "single process" deployment model (see above) still needs civetweb's static-file serving wired up to `frontend/dist/` for a production build.
